# Feature Specification: 数据层韧性重构（多源可插拔 + 限流治理 + 冷热分离 + 缓存）

**Feature Branch**: `003-data-source-resilience`

**Created**: 2026-07-04

**Status**: Draft

**Input**: 见 [research.md](../002-market-observation-platform/research.md) 之后的数据源调研（29 智能体并行 + 一手来源复核）；本 spec 重构 QuantChive「数据怎么进来」这一层，不改上层观测模型/查询/可视化。

## 背景

QuantChive 现状：数据获取**单一直连东财**（`push2delay`/`push2his.eastmoney.com` + akshare）。调研（经一手来源复核）确认三个根本问题：

1. **限流**：东财自 2025-04 对 IP 限频。本项目高频翻页（全市场个股 2→56 页**页间零 sleep**、退避无 jitter）已多次把 IP 打进冷却，采集降级为只返当日 1 条。**换库不解决**——akshare/efinance 底层同为 `push2his`。
2. **历史深度缺失**：盘中快照只能向前积累；东财历史端点在限流下不可靠；缺独立于东财的历史回填层。
3. **无缓存**：多指标复用同一 clist 重复回源；历史/日终数据（收盘不变）每次重打。

本重构的核心判断：**出路是「主动节流 + 本地缓存 + 冷热分离 + 多源分流」，不是换数据提供方。**

## Clarifications

### Session 2026-07-04

- Q: 历史行情/时序的默认回填源用哪个？ → A: **baostock 作默认历史源**（免 token、日/周/月/分钟 K 深至 1990、有前后复权、无 IP 限流；短板无资金流——资金流历史仍走东财 fflow/同花顺）。需 `uv add baostock`。
- Q: 同花顺(10jqka) 资金流分流本期做到哪一步？ → A: **本期接入作资金流备源**（东财资金流限流时自动切同花顺）；接入前须小流量验证 `hexin-v` 请求头能否稳定生成，验证不过则降级为「预留接口不启用」并记录。
- Q: 本地 HTTP 缓存怎么落地？ → A: **引入 requests-cache**（透明缓存，按端点 glob 差异化 TTL：历史/日终长 TTL、实时快照短 TTL 或不缓存）；经现有可注入 http_get 注入 CachedSession，测试用内存后端不落盘。需 `uv add requests-cache`。
- Q: 限流治理的可测验收硬指标（SC-001）？ → A: **零静默降级为硬门**——压测下数据源降级（请求全量却只回极少条）必须被识别、记审计、拒绝落残缺数据，绝不出现「静默把 1 条当历史」；用 mock 精确可测，不依赖真实限流阈值。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 高频采集不再被限流封禁 (Priority: P1)

作为运维/调度，我希望平台**持续高频采集全市场数据而不把数据源 IP 打进冷却**，这样盘中定时采集能稳定运行、时序数据能连续积累，不再出现「采集降级为只返 1 条」的静默故障。

**Why this priority**: 这是当前最痛的阻断性问题——限流一触发，所有下游（排行/下钻/时序）数据停止更新，且是静默的（看似成功实则丢数据）。不解决它，平台无法长期运行。改动集中在 HTTP 客户端层，风险最低、收益最大，是「止血」。

**Independent Test**: 用可注入的 mock http_get 驱动一次全量翻页采集，断言：(a) 相邻页请求之间有节流等待（不为零）；(b) 重试退避带随机抖动（同 attempt 多次退避时长不恒等）；(c) 对已缓存的历史/日终端点二次请求命中缓存、不再发起真实请求。全程不联网。

**Acceptance Scenarios**:

1. **Given** 一次需翻 56 页的全市场采集, **When** 采集执行, **Then** 每翻一页前有可配置的节流等待（默认随机区间），采集总请求节奏受控。
2. **Given** 数据源返回限流错误, **When** 客户端重试, **Then** 退避时长为「指数基数 + 随机抖动」，多次重试的间隔不呈固定倍数指纹。
3. **Given** 同一历史/日终端点在缓存窗口内被请求两次, **When** 第二次请求, **Then** 直接返回缓存结果，不产生真实网络请求。
4. **Given** 一次采集实际被数据源降级（请求全量却只回极少条）, **When** 采集完成, **Then** 系统显式识别为「限流降级」并记录审计，**不把降级的残缺数据当完整数据落库**（宁缺勿假）。

### User Story 2 - 历史数据一次回填、增量补缺、不受东财限流影响 (Priority: P1)

作为用户/分析者，我希望能看到主体（个股/板块）**过去足够长时段的历史时序**，且这份历史**回填一次即入库权威**、之后只增量补缺、不因东财限流而中断——这样时序图/回看有真实深度，不再只有「今天几个点」。

**Why this priority**: 用户已明确反馈「时序图只有今天，没有历史」。历史回填必须走**独立于东财限流**的路径才可靠。这是用户可感知的价值兑现，与 P1 止血并列。

**Independent Test**: 用 mock 历史源返回 N 个交易日的历史数据，执行回填，断言：(a) N 天历史入库为日终观测；(b) 记录「该主体该指标已存时间区间」；(c) 二次回填仅请求缺失区间、不重复拉已存区间；(d) 若历史源某主体失败，隔离不影响其他主体。全程不联网。

**Acceptance Scenarios**:

1. **Given** 某主体无历史数据, **When** 执行历史回填, **Then** 该主体近 N 个交易日的历史时序入库，时序回看可见真实深度。
2. **Given** 某主体已回填至日期 D, **When** 再次执行回填, **Then** 系统据「已存区间」只请求 D 之后的缺口，不重复拉取已存历史。
3. **Given** 历史行情源（不受东财限流）与实时快照源并存, **When** 查询某主体时序, **Then** 历史段与近实时段拼接呈现且口径一致（字段/标度归一），断点不连线。
4. **Given** 回填过程中某主体请求失败, **When** 回填继续, **Then** 失败主体被隔离并计入审计，其余主体正常回填（断点=缺行不造假）。

### User Story 3 - 数据源可插拔、按指标类型主备切换、单源故障不瘫痪 (Priority: P2)

作为平台维护者，我希望**每类数据（资金流/行情/历史/财务）绑定「优先源 + 备用源」**，主源不可用（限流/改版/宕机）时自动切到备源；也希望新增数据源时**只写一个源适配器、不改上层业务**——这样平台摆脱「单点数据源」的命运，长期可维护。

**Why this priority**: 这是根治「单源命运」的架构升级，但依赖 P1/P2 的节流与冷热分离先落地；属于韧性增强而非阻断性止血，故 P2。现有 `ObservationSource` Protocol + `source_id` 的可插拔 seam 已就位，成本可控。

**Independent Test**: 注册两个 fake 源（主源抛限流错、备源正常），对同一类指标发起采集，断言自动切到备源产出正确数据；再用一个只实现 Protocol 的全新 fake 源替换，断言上层排行/采集不改仍跑通（SC-008 换源不改上层）。全程不联网。

**Acceptance Scenarios**:

1. **Given** 某类指标配置了主源与备源, **When** 主源返回限流/失败, **Then** 系统自动改用备源取数，采集成功且审计记录实际使用的源。
2. **Given** 一个全新数据源仅实现统一源接口, **When** 注册并指定为某类指标的源, **Then** 上层查询/采集/可视化代码零改动即可消费其数据。
3. **Given** 配置指向一个未安装/缺失的源, **When** 系统初始化, **Then** 优雅降级（不崩溃），明确提示该源缺失，其余源正常工作。

---

### User Story 4 - 采集纪律统一固化，失败标的分轮重取、完整性校验 (Priority: P3)

作为平台维护者，我希望所有源的**批量采集遵循统一的限流纪律**——低并发、请求间节流、失败标的分轮重试、数据太短判为未取全并下轮重取——这样不必在每个源里重复实现且不会因某个源写得糙而触发封禁。

**Why this priority**: 工程质量收敛，把散落的节流/重试纪律沉淀成可复用基类。价值在可维护性与稳健性，非用户直接可感知，故 P3。

**Independent Test**: 用 mock 源制造「部分标的首轮失败 + 部分标的返回过短数据」，跑采集基类，断言：失败与过短标的进入下一轮重取、达到重试上限后如实计入失败审计、并发受限为单写者。全程不联网。

**Acceptance Scenarios**:

1. **Given** 一批标的中部分首轮请求失败, **When** 采集基类执行, **Then** 仅对失败标的做有限轮次重取，成功则补齐、超限则如实计失败。
2. **Given** 某标的返回的数据长度短于预期阈值, **When** 完整性校验, **Then** 判为未取全并纳入下轮重取，不把残缺当完整。

---

### Edge Cases

- **数据源静默降级**：请求全量却只回当日 1 条（本项目已实测的限流表现）——必须靠「预期条数/长度校验」识别为降级，不落库、记审计，而非当成功。
- **缓存陈旧**：历史/日终端点缓存 TTL 设置后，收盘前的当日数据若被长 TTL 缓存会读到过期值——须区分「已收盘不变的历史」与「盘中可变的当日」，只对前者长缓存。
- **多源口径不一致**：不同源对同一主体的字段名/单位/复权口径不同（如成交量手 vs 股、净额元 vs 亿元）——归一层必须把标度统一到项目内部约定（金额整数分等），否则跨源拼接的时序数值错乱。
- **备源也不可用**：主备源同时失败——须如实报错并记审计，不静默返回空当作「无数据」误导用户。
- **增量缺口边界**：已存区间与新请求区间在端点日重叠或相邻——补缺逻辑须正确处理含左不含右等边界，不重复写、不漏日。
- **历史源无某类指标**：如纯行情历史源没有资金流——须诚实按能力自描述，不伪造缺失指标（延续 FR-004 能力自描述原则）。

## Requirements *(mandatory)*

### Functional Requirements

**限流治理（US1）**

- **FR-001**: 翻页采集在**相邻页请求之间**必须插入可配置的节流等待（默认随机区间，避免固定节奏指纹）；节流参数可注入以便测试。
- **FR-002**: 重试退避必须为「指数基数 + 随机抖动」，使多次重试的间隔不呈固定倍数；退避参数可配置。
- **FR-003**: 系统必须提供**透明的本地 HTTP 缓存**能力（经 requests-cache 经现有可注入 http_get 注入 CachedSession 实现）：对**已收盘不变的历史/日终数据**长 TTL 缓存、对**盘中可变的实时快照**短 TTL 或不缓存（按端点 glob 差异化 TTL）；缓存后端可注入（测试用内存后端，不落盘不联网）。
- **FR-004**: 系统必须区分「实时/可高频端点」与「历史/须缓存端点」，二者可配置不同的节流与缓存策略。
- **FR-005**: 采集必须能识别**数据源限流降级**（请求全量却只回极少条/过短），显式记为限流并计入审计，且**不把降级的残缺数据当完整数据落库**。

**冷热分离 + 历史回填（US2）**

- **FR-006**: 系统必须支持从**独立于当前主源限流**的历史数据源回填主体的历史时序，写为日终观测（沿用现有观测模型，不改 schema 主结构）。
- **FR-007**: 系统必须维护「**主体 × 指标 已存时间区间**」记录，用于增量更新与缺口检测。
- **FR-008**: 历史回填必须是**增量**的：据「已存区间」只请求缺失区间，不重复拉取已存历史；回填幂等（重复运行不产生重复行/不破坏已存数据）。
- **FR-009**: 历史段与近实时段的时序在查询层必须**口径一致**地拼接（字段/标度经归一），断点保持 null 不连线（延续现有 series 语义）。
- **FR-010**: 单主体回填失败必须被隔离，不影响其他主体；失败计入审计（断点=缺行不造假）。
- **FR-011**: 回填深度必须可配置，默认对齐保留窗口；不做全历史（自建完整历史集是后续）。

**多源可插拔 + 故障切换（US3）**

- **FR-012**: 系统必须提供**按源标识选源的工厂**，并在指定源缺失/未安装时**优雅降级**（不崩溃、明确提示），其余源不受影响。
- **FR-013**: 系统必须支持**每类指标（资金流/行情/历史/财务）绑定「优先源 + 备用源」**；优先源不可用（限流/失败）时自动切换到备用源，审计记录实际使用的源。本期具体配置：**资金流 → 东财（主）/ 同花顺 10jqka（备）双活**；历史行情 → baostock；实时行情/快照 → 东财。
- **FR-014**: 新增数据源必须**只需实现统一源接口**（现有 `ObservationSource` seam），上层查询/采集/可视化代码零改动即可消费（SC-008 换源不改上层）。
- **FR-015**: 多源数据必须经**归一层**把字段名/单位/复权口径统一到项目内部约定（金额整数分等），保证跨源拼接数值正确。

**采集纪律（US4）**

- **FR-016**: 系统必须提供**统一的批量采集纪律**：低并发（单写者约束）、请求间节流、失败标的分轮有限重试、数据完整性校验（过短判未取全）后下轮重取；各源复用此纪律而非各自实现。

**贯穿约束（宪章）**

- **FR-017**: 所有源适配、节流、缓存、故障切换、回填必须**可注入 mock 测试且不联网**（宪章 IV）；HTTP 客户端与时钟可注入。
- **FR-018**: 历史回填必须**无前视**：只写真实交易日期的历史值，不用未来值回填空档（宪章 II）。
- **FR-019**: 每次采集/回填必须产生结构化审计记录（三态 + 实际使用的源 + 限流降级标记）；禁止无声吞异常（宪章 V）。
- **FR-020**: 多源归一后金额/数值必须保持**整数最小单位**表示，禁 float 参与货币计算（宪章 III）。

### Key Entities *(include if feature involves data)*

- **数据源（Source）**：一个可插拔的取数适配器，有稳定 `source_id`、声明其能提供的指标能力、实现统一取数接口。多个源可服务同一类指标（主/备）。
- **源路由（Source Routing）**：「指标类型 → 优先源 + 备用源」的配置与选源/切换逻辑；含缺失源的优雅降级。
- **已存区间记录（Coverage Range）**：记录「主体 × 指标」已入库的时间区间，驱动增量回填与缺口检测。历史入库即权威。
- **归一层（Normalizer）**：把各源异构字段/单位/复权口径统一到项目内部标度约定的转换层，是多源拼接数值正确的保证。
- **HTTP 客户端节流/缓存**：承载页间节流、退避抖动、透明缓存策略的取数底座；客户端可注入。
- **采集审计（Ingestion Run）**：延续现有 `ingestion_run`，扩展记录「实际使用的源」与「限流降级」标记。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: **零静默降级（硬门）**——在受控高频采集压测下（mock 模拟数据源被限流、请求全量却只回极少条），系统必须 100% 将其识别为限流降级、记入审计、拒绝落库残缺数据；绝不出现「静默把降级的 1 条当完整历史/快照落库」。此指标用 mock 精确可测，不依赖真实限流阈值。此外页间节流与退避抖动生效，采集能连续运行不因高频触发冷却。
- **SC-002**: 用户能查看主体**近 N 个交易日（默认对齐保留窗）的历史时序**，时序图不再「只有今天」；历史段真实、断点 null 不连线。
- **SC-003**: 二次历史回填的网络请求量相较首次**大幅下降**（仅补缺口），且重复回填不产生重复数据、不破坏已存历史。
- **SC-004**: 主源故障（限流/失败）时，配置了备源的指标类型**自动切换到备源并成功取数**；审计如实记录实际使用的源。
- **SC-005**: 新增一个仅实现统一源接口的数据源，**上层查询/采集/可视化代码零改动**即可消费其数据（延续 SC-008 换源不改上层）。
- **SC-006**: 全部源适配/节流/缓存/故障切换/回填逻辑**可在不联网下用 mock 测试覆盖**，测试全绿（宪章 IV）。
- **SC-007**: 多源拼接的时序在**同一主体同一指标上口径一致**（抽样核对字段/标度归一正确），金额保持整数最小单位、无 float 精度问题。

## Assumptions

- **不改上层**：本期只重构「数据怎么进来」——观测数据模型（subject/observation）、查询 Service、只读 API、可视化均不改；现有 `ObservationSource` Protocol + `source_id` 的可插拔 seam 复用。
- **主源仍为东财实时**：东财在实时快照/资金流上仍是主力（其擅长且社区实测实时端点限流较松）；限流治理让它可持续高频，而非弃用。
- **历史行情源 = baostock（已定）**：默认引入 baostock 作历史回填层——免登录 token、日/周/月/分钟 K 深至 1990、有前后复权、无 IP 限流。**其短板是无资金流**——资金流历史仍走东财 fflow（受限流，靠缓存+节流缓解）或同花顺分流。需 `uv add baostock`。
- **同花顺（10jqka）= 资金流备源（本期接入，已定）**：东财资金流限流时自动切同花顺。**风险前置**：其 `hexin-v` 请求头依赖 JS 生成——接入第一步须小流量验证能否稳定生成；若验证不过，降级为「预留接口不启用」并记录，不阻塞其余能力。
- **HTTP 缓存 = requests-cache（已定）**：透明缓存、按端点 glob 差异化 TTL、经可注入 http_get 注入 CachedSession；测试用内存后端不落盘。需 `uv add requests-cache`。注意改 TTL 不回溯已有条目，优先注入显式 CachedSession 实例而非全局 install_cache。
- **落库暂留 SQLite**：稳定历史时序的列式落盘（parquet/DuckDB）为演进方向，本期抓取层与落库层解耦但仍落 SQLite。
- **不做的**：付费源作主路径（tushare 仅可选财务补充）、动态代理池（预留抽象不实现）、全历史数据集（回填深度配置化）。
- **诚实认知**：换库不绕限流已证；限流阈值无官方数字（~1000/天为社区轶事下界，宜当保守下界）；新源接入前须小流量验证真实字段/限流表现，不臆测。
- **依赖引入走 uv add**：新增第三方源库（如历史行情源、requests-cache 类缓存）须经 `uv add`，不手改 uv.lock（宪章技术约束）。
